# 1️⃣ Домен: какие факты о мире мы храним

## Основные сущности

### 1. Пользователь (Customer)

Факт: существует человек или компания, которая покупает продукты.

Храним:

* кто он
* как аутентифицируется
* какие лицензии ему выданы

Инварианты:

* email уникален
* пользователь может иметь 0..N лицензий

---

### 2. Продукт (Product)

Это абстрактная сущность:
**"то, что продаётся"**

Типы продукта:

* Sample Pack
* Plugin

Инварианты:

* у продукта есть чёткий тип
* имя уникально в рамках магазина
* продукт может иметь несколько версий (если это плагин)

---

### 3. Версия плагина (Plugin Version)

Факт:

> Плагин X существует в версии 1.0.0, 1.1.0 и т.д.

Храним:

* семантическую версию
* поддерживаемую платформу
* build hash
* минимальную совместимую версию протокола лицензирования

Инварианты:

* (plugin_id, version_string, platform) — уникальны
* версия immutable (не редактируется задним числом)

---

### 4. Платформа

Факт:

* Windows
* macOS
* Linux

Это не строка, а контролируемый enum.

---

### 5. Заказ (Order)

Факт:

> Пользователь купил N продуктов в рамках транзакции.

Инварианты:

* заказ immutable после оплаты
* сумма фиксируется в момент оплаты
* заказ имеет статус (pending / paid / failed / refunded)

---

### 6. Лицензия (License)

Ключевая доменная сущность.

Факт:

> Пользователь имеет право использовать конкретный продукт.

Храним:

* к какому продукту относится
* кому выдана
* дата выдачи
* срок действия (если есть)
* статус (active / revoked / expired)
* ограничения по активациям

Инварианты:

* лицензия привязана к одному пользователю
* лицензия относится к одному продукту
* revoked ≠ deleted

---

### 7. Активация (Activation)

Факт:

> Конкретная копия плагина активирована на конкретном устройстве.

Храним:

* license_id
* device_fingerprint
* публичный ключ клиента (если mTLS)
* версия плагина
* время активации
* последний check-in

Инварианты:

* количество активных активаций ≤ лимита лицензии
* device_fingerprint уникален в рамках license

# 3️⃣ Модель лицензирования с mTLS

Ты хочешь mTLS — отлично, это серьёзный подход.

### Модель:

1. При первой активации:

   * Плагин генерирует keypair
   * Отправляет CSR
   * Сервер выпускает клиентский сертификат
   * Сертификат привязывается к Activation

2. При проверке лицензии:

   * Плагин подключается по mTLS
   * Сервер:

     * валидирует сертификат
     * находит activation по public_key
     * проверяет статус license
     * проверяет не revoked ли activation

### Тогда в БД появляется:

Activation:

* client_public_key (UNIQUE)
* certificate_serial (UNIQUE)
* revoked_at

Инвариант:

* сертификат нельзя переиспользовать для другой лицензии

# 4️⃣ Нормализованная логическая схема (3NF)

(логический уровень, не SQL)

---

## User

* id (PK)
* email (UNIQUE)
* password_hash
* created_at
* status

---

## Product

* id (PK)
* name (UNIQUE)
* type (ENUM: sample_pack, plugin)
* description
* price_cents
* currency
* created_at
* is_active

---

## Plugin

(если хочешь разделить plugin и sample_pack жёстко)

* id (PK)
* product_id (FK UNIQUE)
* internal_code
* default_activation_limit

---

## PluginVersion

* id (PK)
* plugin_id (FK)
* version (semver string)
* platform (ENUM: win, mac, linux)
* build_hash
* min_license_protocol_version
* created_at

UNIQUE(plugin_id, version, platform)

---

## Order

* id (PK)
* user_id (FK)
* total_amount_cents
* currency
* status
* created_at
* paid_at

---

## OrderItem

* id (PK)
* order_id (FK)
* product_id (FK)
* price_at_purchase

---

## License

* id (PK)
* user_id (FK)
* product_id (FK)
* order_item_id (FK)
* activation_limit
* issued_at
* expires_at NULLABLE
* revoked_at NULLABLE
* status

---

## Activation

* id (PK)
* license_id (FK)
* device_fingerprint
* client_public_key (UNIQUE)
* certificate_serial (UNIQUE)
* plugin_version_id (FK)
* activated_at
* last_checkin_at
* revoked_at NULLABLE

UNIQUE(license_id, device_fingerprint)

# 5️⃣ Где мы избегаем NULL

Плохо:

```
revoked BOOLEAN
```

Лучше:

```
revoked_at TIMESTAMP NULL
```

Потому что:

* NULL = не отозвана
* NOT NULL = отозвана
* ещё и время известно

---

# 6️⃣ Soft delete vs Hard delete

Для:

* License
* Activation
* Order

→ **Hard delete запрещён**

История финансов и лицензий — immutable.

Для:

* Product
* PluginVersion

→ используем `is_active`

# 8️⃣ Транзакционная модель

### Активация лицензии:

Транзакция:

1. SELECT active activations FOR UPDATE
2. Проверить лимит
3. INSERT activation
4. COMMIT

Isolation: READ COMMITTED достаточно
Retry при deadlock

# 9️⃣ Индексы (проектируются по запросам)

Обязательно:

* License(user_id, product_id, status)
* Activation(license_id)
* Activation(client_public_key)
* PluginVersion(plugin_id, platform)
* Order(user_id)

Не делаем индекс на каждую колонку.

# 🔟 Что важно для JUCE плагина

Плагин должен хранить:

* license_token
* client private key
* certificate
* device id

И:

* периодически делать check-in
* поддерживать offline grace period

# 11️⃣ Версионирование протокола лицензирования

Очень важно.

В PluginVersion:

* min_license_protocol_version

В LicenseServer:

* current_protocol_version

Это позволит:

* не ломать старые плагины
* эволюционировать API

---

# 12️⃣ Что НЕ делать

❌ хранить JSON blob вместо схемы
❌ не использовать FK
❌ делать polymorphic product_id + product_type без строгой модели
❌ удалять лицензии
❌ хранить даты в локальном времени

---

# 💡 Архитектурно

Лучше разделить:

* API для магазина
* License Server (отдельный сервис)
* CA (certificate authority) для mTLS

Можно объединить логически, но лучше разделить ответственность.
